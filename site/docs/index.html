documentation · ctx 0.2.0

Give your agent's context a lockfile.

Ctx records exactly which bytes an agent read — every policy, document, or dataset, by content hash — so any run can be diffed against another, replayed byte for byte without touching the live source, and exported as evidence.

Models are probabilistic, but many context failures are infrastructural. Agent reliability is bounded by context reliability.

Quickstart (embedded, no services) Use it from Claude Code via MCP TypeScript SDK 
# The whole idea in six commands. Real output, hashes trimmed.
$ ctx resource add ctx://demo/policies/refunds --source-type filesystem --path policies/refunds.md --policy require_fresh
$ ctx run --id run-a ctx://demo/policies/refunds
Mounted ctx://demo/policies/refunds -> snapshot snap_01M0HRB5KJ… (position 0)
Committed manifest manifest_01M0HRB5KJ… for run run-a (1 entry)
$ ctx tag set ctx://demo/policies/refunds prod snap_01M0HRB5KJ…        # promote what run-a saw
$ printf 'Products can be refunded within 14 days.\n' > policies/refunds.md   # the source changes underneath
$ ctx run --id run-b ctx://demo/policies/refunds
$ ctx diff run-a run-b
~ ctx://demo/policies/refunds  (snap_01M0HRB5KJ… -> snap_01M0HRB68R…)
  why: source revision sha256:c8b0bb212e93 → sha256:8f4b00474456; observed 08:52:32Z → 08:52:33Z

  +Products can be refunded within 14 days.
$ ctx replay run-a                                  # reads the store, never the file

Replay verified: SHA256 match for 1/1 entries.
$ ctx evidence export run-a --with-content --out bundle.json && ctx evidence verify bundle.json
evidence verified: 1 entry, merkle root 8482a767…, embedded content 1/1 re-hashed, replay match 1/1

What it is

A small Go binary (ctx) plus an optional server (ctxd) that sits underneath your retrieval, prompting, and memory stack and answers one question forever: which exact bytes went into this run?

What it isn't

Not a vector DB, not an observability tool, not a prompt registry, not memory. It complements install time lockfiles (APM, skills-lock.json) that pin static config — Ctx pins the runtime documents, per run.

Where it plugs in

MCP server for Claude Code / Desktop / Cursor, OpenTelemetry spans with GenAI attributes, a TypeScript SDK, a LangGraph example, and a plain HTTP API. The CLI behaves identically embedded or against a server.

mechanism

How it works

Six primitives, one loop: resolve → manifest → diff → replay. The picture below is the refunds walkthrough above, drawn as data flow.

Source

Where bytes physically live: filesystem, github, or http. Credentials come from ctxd's environment at fetch time and are never stored.

Resource

The stable logical identity your code uses: ctx://<namespace>/<path>. Survives the bytes changing.

Policy

Freshness rule per resource: require_fresh (verify again every resolve), allow_stale (reuse within --max-age), or pin with a @tag.

Snapshot

An immutable observation: sha256:… content hash, source revision, observed at, provenance (ETag, path, commit…). Identical bytes dedupe to one blob.

Manifest

The ordered, immutable record of everything a run resolved — position, URI, @ref, snapshot, content hash. Order is an invariant: it changes model input.

Evidence bundle

An in-toto Statement whose subject digest is a Merkle root over the manifest; carries entries, redacted resource definitions, and a replay check. Verifiable by anyone you hand it to.

use it

Install & first resolve

Embedded mode needs only Go 1.26+. Everything lives in a local .ctx directory (SQLite + blobs); no services.

git clone <this repo> ctx && cd ctx
go build -o ctx ./cmd/ctx
./ctx version            # ctx 0.2.0

# register a document: identity + source + freshness policy
./ctx resource add ctx://demo/policies/refunds \
  --source-type filesystem \
  --path examples/refund-agent/policies/refunds.md \
  --policy require_fresh

# resolve it (creates the first snapshot)
./ctx get ctx://demo/policies/refunds
uri:          ctx://demo/policies/refunds
snapshot:     snap_01M0HRB5GNVBJ1MYZXCPHA51VZ
content_hash: sha256:c8b0bb212e93151d720746e36ff3b7076727cb577614feafa0d61f168965aedb
freshness:    fresh (observed 2026-08-21T08:52:32Z, policy require_fresh)
provenance:   path=policies/refunds.md source_type=filesystem
bytes:        41
content_type: text/markdown

--- content ---
Products can be refunded within 30 days.

Global flags on every command: --data-dir (embedded; default .ctx or $CTX_HOME), or --server http://… / $CTX_SERVER_URL to talk to a ctxd instead (plus --api-key / $CTX_API_KEY). Output and semantics are identical either way.

Tip. Put export CTX_HOME=$HOME/.ctx in your shell profile so the CLI, the MCP server, and your scripts share one store.

Sources & freshness policies

A resource is where the bytes come from plus how fresh they must be. Three adapters ship in v0.2.

Filesystem

ctx resource add ctx://acme/policies/refunds \
  --source-type filesystem --path /srv/policies/refunds.md --policy require_fresh

GitHub (file in a repo, at a branch or ref)

# GITHUB_TOKEN is read from the ctx/ctxd process environment at fetch time; it is never stored.
export GITHUB_TOKEN=ghp_…
ctx resource add ctx://acme/runbooks/oncall \
  --source-type github --owner acme --repo ops --path runbooks/oncall.md --ref main \
  --policy allow_stale --max-age 1h

The snapshot's source_revision is the commit SHA the file was read at, so ctx diff can later say exactly which commit changed a run's input.

HTTP (any URL; headers may reference env vars)

ctx resource add ctx://acme/pricing/table \
  --source-type http --url https://pricing.internal/v3/table.json \
  --header 'Authorization: Bearer ${PRICING_TOKEN}' \
  --policy allow_stale --max-age 15m

${VAR} references are resolved from the server's environment at fetch time. As defense in depth, sensitive header values (Authorization, Cookie, anything matching *token*/*key*/*secret*…) are masked in every API response, in ctx inspect, and in evidence bundles. ETag and Last-Modified are recorded in snapshot provenance when the server sends them.

Choosing a policy

PolicyBehavior on resolveUse when
require_fresh (default)Verifies again against the source on every resolve. Unchanged bytes dedupe to the same content hash (you'll see two snapshot rows, one blob).Policies, prices, anything where "stale" is a bug.
allow_stale --max-age 1hReuses the current snapshot if it is younger than the TTL; otherwise fetches. --max-age 0 means never refresh once a snapshot exists.Slow or rate limited sources; reference docs that change rarely.
@tag pinResolving ctx://ns/path@prod delivers exactly the tagged snapshot: no fetch, policy not consulted.Promotion workflows (@prod, @v3), reproducible evals, incident fixtures. See Tags.

Inspect what you registered, and the history of what was observed:

ctx resource list
ctx inspect ctx://demo/policies/refunds      # source, policy, tags, current snapshot
ctx history ctx://demo/policies/refunds      # every snapshot, newest first, with TAGS column

Runs, manifests, diff, replay

A run is the unit of work you want to be able to reproduce — one agent turn, one job, one eval case. Mounting a URI into a run resolves it and records it at the next position; committing freezes the run into a manifest.

  1. Record a run

    Single shot form (start + mount + commit) or the three step form if your code mounts across time.

    ctx run --id run-a ctx://demo/policies/refunds ctx://demo/policies/tone
# or, step by step:
ctx run start run-a
ctx run mount run-a ctx://demo/policies/refunds
ctx run mount run-a ctx://demo/policies/tone
ctx run commit run-a
    Started run run-a
Mounted ctx://demo/policies/refunds -> snapshot snap_01M0HRB5KJ2HNJBYH2TV22BBT0 (position 0)
Committed manifest manifest_01M0HRB5KJMHPS0X0GGXF853CP for run run-a (1 entry)

  2. Read the manifest

    ctx manifest run-a        # by run id or manifest id
    Manifest manifest_01M0HRB5KJMHPS0X0GGXF853CP (run run-a), created 2026-08-21T08:52:32Z, 1 entry

POS  URI                          SNAPSHOT                         CONTENT_HASH
0    ctx://demo/policies/refunds  snap_01M0HRB5KJ2HNJBYH2TV22BBT0  sha256:c8b0bb212e93…

  3. Change the world, run again, diff the inputs

    The why: line is the point: not just that the input changed, but which source revision and when it was observed.

    printf 'Products can be refunded within 14 days.\n' > policies/refunds.md
ctx run --id run-b ctx://demo/policies/refunds
ctx diff run-a run-b
    --- run-a (manifest_01M0HRB5KJMHPS0X0GGXF853CP)
+++ run-b (manifest_01M0HRB68SZDF1N6TTNXC0VQCT)

~ ctx://demo/policies/refunds  (snap_01M0HRB5KJ… -> snap_01M0HRB68R…)
  why: source revision sha256:c8b0bb212e93 → sha256:8f4b00474456; observed 2026-08-21T08:52:32Z → 2026-08-21T08:52:33Z
  --- a/ctx://demo/policies/refunds
  +++ b/ctx://demo/policies/refunds
  @@ -1,2 +1,2 @@
  -Products can be refunded within 30 days.
  +Products can be refunded within 14 days.

1 resource changed, 0 added, 0 removed, 0 unchanged

  4. Replay — the invariant

    replay rebuilds a manifest's bytes from the content addressed store and hashes them again. It never contacts the source, so it works after the file changed, after the API key expired, after the repo was archived. Any mismatch or missing blob exits nonzero.

    ctx replay run-a
    Replaying manifest manifest_01M0HRB5KJMHPS0X0GGXF853CP (run run-a), 1 entry

[0] ctx://demo/policies/refunds
    materialization: mat_01M0HRB5KJHXZ6DHBAX3XN74NC
    content_hash (recorded):  sha256:c8b0bb212e93…
    content_hash (replayed):  sha256:c8b0bb212e93…
    match: OK

--- content ---
Products can be refunded within 30 days.

Replay verified: SHA256 match for 1/1 entries.
Design note. Entry order is part of the manifest's identity — two runs that read the same documents in a different order are different runs, because the model saw different input. Ctx commits to the order; it never sorts it away.

Tags: @prod and friends

A tag is a named, movable pointer (resource, tag) → snapshot. It turns "the policy we reviewed on Tuesday" into something code can ask for by name — and something a manifest records.

# point prod at the snapshot run-a delivered
ctx tag set ctx://demo/policies/refunds prod snap_01M0HRB5KJ2HNJBYH2TV22BBT0
ctx tag list ctx://demo/policies/refunds
ctx tag rm   ctx://demo/policies/refunds prod

# resolve by tag: no fetch, policy not consulted
ctx get ctx://demo/policies/refunds@prod
ctx run --id run-c ctx://demo/policies/refunds@prod
ctx manifest run-c      # shows a REF column: prod
uri:          ctx://demo/policies/refunds@prod
ref:          prod
snapshot:     snap_01M0HRB5KJ2HNJBYH2TV22BBT0
content_hash: sha256:c8b0bb212e93151d720746e36ff3b7076727cb577614feafa0d61f168965aedb
freshness:    tagged (@prod -> snapshot snap_01M0HRB5KJ…, observed 2026-08-21T08:52:32Z, policy not consulted)

--- content ---
Products can be refunded within 30 days.   # even though the file now says 14
  • Tag names match ^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$; a tag can only point at a snapshot of its own resource.
  • Manifest entries store the bare URI plus the ref they were mounted by — moving a tag later can never change what a committed manifest replays.
  • Deleting a tag doesn't delete the snapshot; old manifests still replay.
  • Typical flow: every run uses require_fresh in staging; a reviewer runs ctx history, picks a snapshot, tag set … prod; production mounts @prod. Promotion is a pointer move, audited in history's TAGS column.

Evidence bundles

When someone asks "what did the agent actually see for this decision?", hand them a file. ctx evidence export produces an in-toto Statement whose subject digest is a Merkle root over the run's entries; ctx evidence verify checks it — offline if you like.

ctx evidence export run-a --with-content --out bundle.json
ctx evidence verify bundle.json             # also cross-checks against the store via replay
ctx evidence verify bundle.json --offline   # merkle root + embedded content only
evidence bundle written to bundle.json: 1 entry, merkle root 8482a7671b1d7ba1081f4a7b3a3e7400a3ab58dc3a3687430bae6fa316adbd68
evidence verified: 1 entry, merkle root 8482a767…, embedded content 1/1 re-hashed, replay match 1/1

Shape (trimmed):

  "_type": "https://in-toto.io/Statement/v1",
  "subject": [{ "name": "manifest_01M0…", "digest": { "sha256": "8482a767…" } }],
  "predicateType": "urn:ctx:evidence:v0.2",
  "predicate": {
    "run_id": "run-a", "manifest_id": "manifest_01M0…",
    "merkle": { "algorithm": "sha256",
                "leaf": "sha256(position_be_uint32 || 0x00 || uri || 0x00 || content_hash)",
                "root": "8482a767…" },
    "entries": [{ "position": 0, "uri": "ctx://demo/policies/refunds", "ref": "prod",
                  "snapshot_id": "snap_01M0…", "content_hash": "sha256:c8b0bb21…",
                  "source_revision": "sha256:c8b0bb212e93", "observed_at": "2026-08-21T08:52:32Z",
                  "content_type": "text/markdown", "bytes": 41,
                  "provenance": { "path": "policies/refunds.md", "source_type": "filesystem" },
                  "content_b64": "UHJvZHVjdHMgY2FuIGJl…" }],
    "resources": [{ "uri": "ctx://demo/policies/refunds",
                    "source": { "kind": "http", "config": { "http": { "headers": { "Authorization": "[REDACTED]" } } } },
                    "policy": { "strategy": "require_fresh" } }],
    "replay": { "all_match": true, "entries": [{ "position": 0, "match": true }] }
  }
}

What it proves

That these bytes (by hash, optionally embedded) were delivered for this run, in this order, under these resource definitions, and that the store can still reproduce them. The root ties the whole run to one digest.

What it doesn't

That the model used them, or that the source was authoritative. Bundles aren't signed yet (roadmap: cosign/in-toto attestation). Tamper with an entry and verify fails; reroot a forged bundle and only the store cross check catches it — so keep --offline for transport, not trust.

Where it fits

EU AI Act Art. 12 automatic logging (Annex III systems, from 2 Aug 2026) and SOC 2 "what data did the agent consider" reviews want exactly this record. Not legal advice — what you owe depends on your system and jurisdiction.

The same bundle can be built client side from the TypeScript SDK (buildEvidence) with a byte identical Merkle root, and exported by an agent through the MCP tool ctx_evidence_export.

integrate

Client/server mode & HTTP API

ctxd is the same engine behind an HTTP API, backed by Postgres + an S3-compatible store (MinIO in dev). Teams, services, and the MCP server share one history.

# full stack from a clean clone: Postgres + MinIO + ctxd (+ an OTel collector)
cp .env.example .env        # change the dev-only credentials
docker compose up -d --build
curl http://localhost:8080/healthz      # ok

# point the CLI at it — every command works identically
export CTX_SERVER_URL=http://localhost:8080
ctx resource add ctx://demo/hello-world --source-type http \
  --url https://raw.githubusercontent.com/octocat/Hello-World/master/README --policy require_fresh
ctx get ctx://demo/hello-world
Containerized ctxd can't see your host filesystem. Use GitHub/HTTP sources there, or mount the files. For local on the host work, run ctxd directly in embedded mode: go build -o ctxd ./cmd/ctxd && ./ctxd --addr :8080 --data-dir ~/.ctx (omit --postgres-dsn).

ctxd flags (all also settable as CTXD_* env vars)

ctxd --addr :8080 \
     --postgres-dsn 'postgres://ctx:***@localhost:5434/ctx?sslmode=disable' \
     --s3-endpoint localhost:9000 --s3-access-key … --s3-secret-key … --s3-bucket ctx-blobs [--s3-use-ssl] \
     --api-key "$CTXD_API_KEY"      # when set, every request except /healthz needs Authorization: Bearer <key>

TypeScript SDK

@ctx/sdk is a typed, zero dependency client for ctxd (Node 18+ fetch). Every method maps to one endpoint; buildEvidence composes a bundle client side.

cd sdk/typescript && npm install && npm run build && npm link   # not on a registry yet
import { Ctx, buildEvidence, encodeEvidence } from "@ctx/sdk";

const ctx = new Ctx({ endpoint: "http://localhost:8080", apiKey: process.env.CTX_API_KEY });

// one-off resolve
const policy = await ctx.resolve("ctx://acme/policies/refunds");
policy.content;                  // the bytes, decoded to text
policy.snapshot.content_hash;    // "sha256:…"

// record a run: mount = resolve + append to the manifest (starts lazily)
const run = ctx.run({ id: `turn-${turnId}` });
const refunds = await run.mount("ctx://acme/policies/refunds@prod");   // pinned by tag
const customer = await run.mount(`ctx://acme/customers/${customerId}`);
const manifest = await run.commit();
manifest.manifest_id;            // store this next to the model call / checkpoint

// tags
await ctx.setTag("ctx://acme/policies/refunds", "prod", policy.snapshot.id);
await ctx.listTags("ctx://acme/policies/refunds");
refunds.freshness.status;        // "use_tag"
refunds.resource.ref;            // "prod"

// diff two runs, with the why
const diff = await ctx.diff("turn-41", "turn-42");
for (const e of diff.entries) if (e.status === "changed")
  console.log(e.uri, e.source_revision_a, "->", e.source_revision_b, e.unified_diff);

// replay and evidence
const replay = await ctx.replay(manifest.manifest_id);
replay.entries.every((e) => e.match);                          // true
const bundle = await buildEvidence(ctx, manifest.manifest_id, { withContent: true });
await fs.writeFile("bundle.json", encodeEvidence(bundle));     // `ctx evidence verify` accepts it

Errors are CtxErrors carrying the HTTP status and server message (an unknown tag names both URI and tag). content fields are UTF-8 text; for binary sources prefer the Go exporter for evidence.

MCP: use Ctx from Claude Code, Claude Desktop, Cursor

ctx mcp is a stdio MCP server. Registered documents become readable ctx:// resources (with provenance in _meta), and resolve / runs / diff / replay / tags / evidence become 13 tools the model can call.

Claude Code

# embedded store
claude mcp add ctx -- /abs/path/to/ctx mcp --data-dir /abs/path/to/.ctx

# against a running ctxd (API key via env, not argv)
claude mcp add ctx --env CTX_API_KEY=sk-… -- /abs/path/to/ctx mcp --server https://ctxd.internal

Claude Desktop (claude_desktop_config.json) · Cursor (.cursor/mcp.json)

{
  "mcpServers": {
    "ctx": {
      "command": "/abs/path/to/ctx",
      "args": ["mcp", "--server", "https://ctxd.internal"],
      "env": { "CTX_API_KEY": "sk-…" }
    }
  }
}

Try it — prompts that exercise the loop

  • "Read ctx://demo/policies/refunds and tell me the refund window." → the model calls resources/read; _meta carries snapshot id, content hash, source revision, observed at, decision.
  • "Now read the @prod version." → same resource, decision: use_tag, the pinned bytes.
  • "Start run ticket-1234, mount the refunds and tone policies, commit, and give me the manifest id." → ctx_run_start → ctx_run_mount ×2 → ctx_run_commit.
  • "Diff ticket-1234 against ticket-1200 and explain why any input changed." → ctx_diff returns per side source revision and observation time.
  • "Export evidence for ticket-1234." → ctx_evidence_export returns the bundle JSON.

Resources are served via the template ctx://{namespace}/{+path} (so multi segment paths and @tag both work). Inline content is capped at 1 MiB with a truncation marker and the content hash. Stdio means local trust; --server mode inherits ctxd's API key auth. Details: docs/mcp.md.

LangGraph (and any framework with checkpoints)

The integration pattern is one line of state: mount inside a node, commit, and put the manifest_id in the checkpoint. Whatever can read the checkpoint later can replay the exact bytes of that turn.

// examples/langgraph-ts/src/graph.ts (condensed)
const GraphState = Annotation.Root({
  question: Annotation<string>,
  ctx_manifest_id: Annotation<string>,          // lands in the checkpoint with the rest of state
  ctx_entries: Annotation<MountedEntry[]>({ reducer: (_p, n) => n, default: () => [] }),
  answer: Annotation<string>,
});

async function loadContext(_s: GraphStateType, config: RunnableConfig) {
  const run = ctxClient().run({ id: `langgraph-${threadIdOf(config)}` });
  const entries = [];
  for (const uri of CONTEXT_RESOURCES) {              // e.g. ctx://demo/policies/refunds, …/tone
    const r = await run.mount(uri);
    entries.push({ uri, snapshot_id: r.snapshot.id, content_hash: r.snapshot.content_hash, content: r.content });
  }
  const manifest = await run.commit();
  return { ctx_manifest_id: manifest.manifest_id, ctx_entries: entries };
}
// answer_question prompts the model with exactly `ctx_entries[*].content` — not a second read.
cd sdk/typescript && npm ci && npm run build
go build -o ctxd ./cmd/ctxd && ./ctxd --addr :8080 --data-dir /tmp/ctx-langgraph &      # host-side, so it can read the fixture files
cd examples/langgraph-ts && npm ci && npm run build
npm run start      # runs the graph with a fake in-memory model (real one if ANTHROPIC_API_KEY is set), prints the manifest id
printf 'Products can be refunded within 14 days.\n' > ../refund-agent/policies/refunds.md
npm run replay     # replays the checkpointed manifest: still "30 days", flags the live source as CHANGED

Same shape works for Temporal/Restate activities (put ctx.resolve in an activity, the manifest id in the event history) and for plain request handlers (log the manifest id with the request id).

Observability

Every stage is traced; set OTEL_EXPORTER_OTLP_ENDPOINT and spans flow. Unset, instrumentation is a no op. Content is never attached to spans or metrics.

│  ├─ ctx.tag.lookup
│  ├─ ctx.cache.lookup                ctx.cache.hit=true
│  └─ ctx.materialize
└─ ctx.manifest.append

  • ctx.manifest.merkle_root on the commit span equals the evidence bundle's subject digest — a trace and a bundle join on one field.
  • gen_ai.data_source.id follows the OpenTelemetry GenAI semantic conventions (ctx://<namespace>), so Phoenix, Langfuse, LangSmith, Datadog, Honeycomb can correlate retrieval by source. The proposal to carry content_hash/source_revision/uri on gen_ai.retrieval.documents is in docs/observability.md.
  • Metrics: ctx_resolve_total/_duration_seconds/_errors_total, ctx_cache_hit_total/_miss_total, ctx_source_fetch_*, ctx_snapshot_created_total, ctx_manifest_created_total, ctx_run_committed_total, ctx_tag_resolve_total.

FAQ & status

Does Ctx replace my RAG pipeline / vector DB?

No. Ctx is about the source documents and what a run actually received. Keep retrieving however you do; mount what you retrieved (or the documents you retrieved from) so the run is reproducible. Derived chunk materializations are on the roadmap; v0.2 delivers raw bytes only.

What happens when the source is unreachable?

require_fresh fails the resolve (no silent staleness). allow_stale serves the cached snapshot if within --max-age. @tag never touches the source. replay never touches the source either.

How is this different from logging tool outputs in my tracing tool?

Traces key on spans; Ctx keys on source identity. You get a freshness policy, a run to run diff of inputs with the source revision that changed, and byte exact replay without fetching again — and the manifest's Merkle root shows up in your trace, so the two complement each other.

Is the store encrypted / multi tenant / signed?

v0.2 is a security baseline: no plaintext credentials at rest (env refs resolved at fetch time, redaction everywhere), optional single API key on ctxd, dev only Compose credentials clearly labeled, dependency scanning clean. Not enterprise IAM; bundles aren't signed yet. See the roadmap.
